# CLAUDE.md

Hinweise für Claude Code beim Arbeiten in diesem Repository.

## Projekt

Inventur der Claude-Code-Laufzeitumgebung: MCP-Server, Plugins, Skills, Befehle, Agenten und Hooks, global und in Projekten, mit Bewertung von Überschneidungen, Empfehlungen und Umsetzung per Dashboard, für Claude Code oder Codex. Die Skills aus `~/.agents` gelten auch für andere Agenten, das Inventar reicht also über Claude Code hinaus.

## Aufbau

- Harness: Der Skill nennt beim Start seinen Harness (`build.py --harness claude-code|codex`), `harness.py` merkt ihn sich in `harness.json`, der letzte Start zählt. Claude Code nutzt `inventar.json`, `dashboard.html`, `bewertung.json`; Codex `inventar-codex.json`, `dashboard-codex.html`, `bewertung-codex.json`. Den Codex-Bestand liest `codex.py` aus `~/.codex` und `~/.agents`, in derselben Datenform; Umgebungswerte von MCP-Servern übernimmt es nie, die Nutzung zählt es in `~/.codex/sessions`. Unter Codex gibt es noch keine Aktionen und kein Installieren.
- `build.py` liest den Bestand aus `~/.claude`, `~/.claude.json` und `~/.agents` und schreibt `dashboard.html` und `inventar.json`. Beide sind erzeugt: nicht von Hand bearbeiten, nicht einchecken. Was nur in einem Projekt gilt, steht im Tab „Projekte“, alle anderen Tabs sind global: Skills und Befehle aus `<Projekt>/.claude`, MCP-Server aus `<Projekt>/.mcp.json` und lokal in `~/.claude.json`, jeweils für die Projekte in `~/.claude.json`; was Hooks an Claude zurückgeben, misst `build.py` in den Transkripten der letzten `HOOK_TAGE` Tage unter `~/.claude/projects`. Ob Skills aus `npx skills` ein Update haben, fragt `build.py` per `gh api` bei GitHub ab (Ordner-SHA gegen `skillFolderHash`); ohne `gh` oder Netz fehlt nur diese Angabe. Mit `--harness codex` schreibt es stattdessen über `codex.py` `inventar-codex.json` und `dashboard-codex.html`.
- `bewertung.json` enthält die Urteile: Beschreibung, Empfehlung, Überschneidungsgruppen, Hinweise. Gepflegt über den Skill `/3zero-harness-inventur` in `skill/SKILL.md`; global verfügbar über den Symlink `~/.claude/skills/3zero-harness-inventur` auf diesen Ordner. Mit `suche <Bedarf>` sucht der Skill neue Skills, Plugins und MCP-Server, gleicht sie mit dem Bestand ab und installiert nur nach Bestätigung. Unter Codex gilt `bewertung-codex.json`, verfügbar über den Symlink `~/.codex/skills/3zero-harness-inventur`.
- `server.py` zeigt das Dashboard auf http://127.0.0.1:8765 und führt die dort gewählten Aktionen aus (deinstallieren, deaktivieren, nur manuell). Welche Aktion ein Eintrag anbietet und mit welchem Befehl, legt allein `aktionen()` in `build.py` fest; der Server führt nur aus, was so in `inventar.json` steht. Als Datei geöffnet bleibt das Dashboard nur lesbar. Der Knopf „neu bewerten“ im Seitenkopf startet über `/api/bewerten` einen eigenen Claude-Lauf (`claude -p "/3zero-harness-inventur"`, Opus) mit fester Werkzeugliste: Lesen, Schreiben und `python3`, sonst nichts. Der Tab „Suche“ startet über `/api/suchen` den Such-Modus ohne Rückfragen und nur mit Lese- und Suchrechten (kein Schreiben, kein `python3`, kein `gh`, weil der Lauf fremde Inhalte aus dem Netz liest); die Kandidaten kommen per `--json-schema` zurück. `/api/installieren` installiert nur Skills und Plugins aus der letzten Suche, mit einem Befehl, den der Server aus den geprüften Feldern baut, nie mit Claudes Befehlstext. Bewertung und Suche laufen im Hintergrund (`im_hintergrund()`); der Browser fragt den Stand über `/api/bewertung` und `/api/suche` ab, das Ergebnis bleibt auf dem Server, bis die Karte geschlossen wird. Eine minutenlang offene Anfrage riss beim Neuladen der Seite ab. Unter Codex läuft „neu bewerten“ als `codex exec -s workspace-write` mit `-C` auf einer Arbeitskopie in einem Temp-Ordner, die eine Kopie von `bewertung-codex.json` enthält, nicht im Projektordner; build.py führt der Server davor und danach aus, prüft die zurückgegebene Kopie als JSON-Objekt und schreibt sie atomar zurück. Dabei darf der Lauf weder `$TMPDIR` noch `/tmp` beschreiben (`sandbox_workspace_write.exclude_tmpdir_env_var`, `exclude_slash_tmp`): workspace-write macht sonst auch diese Ordner schreibbar, und ein injizierter Lauf könnte dort etwas ablegen, das `installieren` oder die Claude-Suche später ohne Sandbox ausführen. Die Suche unter Codex läuft `codex exec` mit dem Berechtigungsprofil `suche`: nur lesen, schreiben nur in einen npm-Zwischenspeicher, Zugangsdaten gesperrt (u. a. `.ssh`, `.aws`, `.netrc`, `.npmrc`, `.pypirc`, `.claude.json`, `.codex/config.toml`, `.docker/config.json`, `.kube/config`, `.git-credentials`; `npm_config_userconfig` zeigt dafür auf einen eigenen Pfad), Netz nur über den Codex-Proxy im Modus `limited` zu skills.sh, npm und GitHub, dazu die Websuche (`web_search="live"`) als eigener Kanal außerhalb dieses Proxys. Beide Codex-Läufe ohne eigene Plugins, MCP-Server, Regeln und Apps (`--ignore-user-config --ignore-rules`). `codex exec` braucht leeres stdin, sonst wartet es. Mit VPN kommt der Codex-Proxy nicht durch. `/api/installieren` lehnt der Server unter Codex immer ab.
- Tests: `python3 -m unittest`. Die Server-Tests arbeiten mit harmlosen Befehlen und Temp-Dateien, nie gegen die echte Konfiguration.
- `template.html` ist die Oberfläche. Farben und Bausteine nur aus dem 3zero-Brand-Kit (`../3zero-Design-Kit/BRAND.md`); das Logo bindet `build.py` beim Bauen aus `../3zero-Design-Kit/logo/wordmark.svg` ein (farbig wie auf 3zero.de, ohne den Zusatz „IT- Consulting“: `LOGO_MASSE` kürzt dafür die viewBox). Die Klasse `kopf` ist für Gruppenköpfe vergeben; der feste Seitenkopf heißt `seitenkopf`. Signalfarben sind dort noch offen, deshalb unterscheiden sich die Empfehlungen per Form und Symbol statt per Farbe. Bestätigungen laufen über `frage()` mit einem `<dialog>` im Stil der Service-Card, nie über `confirm()` oder `prompt()`; das Kit hat keinen Dialog-Baustein.
